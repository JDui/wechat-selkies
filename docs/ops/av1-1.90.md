# 1.90 AV1 接入与客户端硬解核查

日期：2026-11-18（Asia/Shanghai）。服务端基线：`AXiVer` / `037178f6c724de14af561470efc69c5d7a07f71a`（1.89）。客户端核查基线：`AXIVER-Client` / `f80b9f9526460e8c7aea8f599f1438a98b6bf49e`（客户端 0.2.3）。

本版完成 AV1 前后端接入，默认仍为 H.264。AV1 的服务端编码严格要求硬件，浏览器解码向 WebCodecs 提交 `prefer-hardware` 提示。当前没有 780M、Windows 客户端和实际 WebCodecs 出帧的端到端测量，不能据此宣称已验证硬编硬解或固定的带宽、CPU、延迟收益。

## 实现范围

| 环节 | 本版行为 |
| --- | --- |
| 采集 / 编码 | X11、全帧、Main profile、8-bit、4:2:0；使用选中的渲染节点 |
| 运行时 | 复用 `/opt/selkies-hevc` 下固定的 `pixelflux==2.2.3`；保留原 H.264 ABI |
| 客户端 | 安全上下文中的 WebCodecs `VideoDecoder`，先探测支持，再按实际码流配置 |
| 视频菜单 | 增加 AV1；客户端不支持或服务端锁定 CPU 时不提供该选项 |
| CPU / 色彩 | 选择 AV1 使用 GPU；AV1 会话关闭全色彩模式，保留原有偏好以便切回其他编码 |
| 几何 | 传输原始桌面尺寸；编码器补齐的边缘在显示前裁切，保持输入坐标一致 |
| 范围限制 | 不提供软件 AV1、10-bit、4:4:4 或 Wayland AV1 路径 |
| 恢复 | 编码初始化、运行健康检查或客户端解码失败时，主控恢复 H.264 |
| 共享观看 | 加入或恢复观看时只重置该观看者并请求关键帧；观看者解码失败只提示该端，不替主控切换编码 |

启动脚本原有的 AMD 探测主要验证 H.264。AV1 选项通过浏览器探测出现，不代表 GPU 已完成 AV1 编码验证；实际选择时还会检查 `hardware_encoders(node)`、`hardware_formats(node)`、首个关键帧及 `stream_info()`。

`SELKIES_ENCODER` 的镜像允许列表增加 `av1enc`，启动默认值校验也接受它。若显式默认 AV1 但已经锁定 CPU 或未发现 DRI，启动仍回退 H.264。既有部署的端口、PIN、网络和 `/config` 配置无需因 AV1 改动。

## 协议与解码

编码名使用 `av1enc`，客户端能力字段为 `av1_supported`。服务端只把这一字段当作该连接的能力；部分设置更新保留其值，新连接重新协商。

AV1 使用独立 WebSocket 二进制类型 `6`，前 10 字节按网络字节序排列：

| 字段 | 长度 | 含义 |
| --- | --- | --- |
| type | 1 字节 | `6` |
| key | 1 字节 | `0` 或 `1`，来自原生 AV1 帧类型 |
| frameId | 2 字节 | 原有 16-bit 帧号，用于有序发送与 ACK |
| y | 2 字节 | 全帧路径固定为 `0` |
| width / height | 各 2 字节 | 原始桌面尺寸 |
| payload | 其余字节 | 一个 temporal unit，采用 AV1 low-overhead OBU 格式 |

原生 pixelflux 的视频包类型 `4` 不能直接作为本项目的 H.264 类型 `4` 发送。适配器读取原生 12 字节头的 codec、frame kind 和帧号，验证 AV1 后转换为类型 `6`。原生 anchor 标志和非关键 INTRA 帧均不会误标为关键帧。

前端读取 Sequence Header OBU，生成实际的 `av01...` codec string，并按解析出的宽高、level 和 bit depth 配置解码器。首次提交必须有包含序列头的可显示关键帧；不会把 HEVC NAL / SPS 规则用于 AV1。AV1 的 WebCodecs 注册规范要求一个 chunk 对应一个 low-overhead temporal unit，且不使用 `description`，本版按该约定实现。[1][2]

AV1 的失败通知使用 `AV1_ENCODER_FALLBACK,<reason>`，与已有 HEVC 通知分开。主控回退只更新编码选择，不重置帧率、质量等其他视频偏好。

### 有界缓存和生命周期

- 后端单个原生包上限 16 MiB；首帧确认前最多保留 120 帧且总量不超过 32 MiB；源宽高上限为 8192。
- 前端编码包、等待配置和在途解码合计最多 48 帧 / 32 MiB；预算涵盖 pending 与 in-flight，避免只限制排队、遗漏已经送入解码器的数据。单个 temporal unit 最多解析 4096 个 OBU，避免大量空 OBU 造成对象分配积压。
- 已解码全帧等待绘制时只保留最新帧，及时关闭替换的 `VideoFrame`，避免隐藏标签页暂停 `requestAnimationFrame` 后积压 GPU / CPU 帧资源。
- 配置异步回调、重连和 reset 使用会话代数隔离；断开、KILL 和关闭会话清理解码器、定时器和待绘帧。
- 启动等待关键帧和客户端等待输出均有超时；服务端每秒核验原生实际编码状态，防止运行时静默降为软件 AV1。

共享观看者加入后必须取得关键帧，因为固定运行时允许无限 GOP。此版本只给新观看者发送 decoder reset，同时向现有 capture 请求关键帧，主控与其他观看者保留引用帧和 ACK 状态。共享连接继续通过原有 PIN / token 校验；已通过鉴权的 viewer 不执行主控接管，也不覆盖主控 WebSocket 或清空其 RTT 数据。

## 小客户端能否使用电脑硬解

**从现有 Windows 客户端架构和启动配置看，可以使用宿主机硬件解码器；本次未实机确认某次会话已经使用硬解。**

审计的是 `AXIVER-Client` 的客户端 0.2.3，工作区保持未修改。证据见以下固定提交文件：

Tauri 在 Windows 使用基于 Chromium 的 WebView2，默认 GPU 渲染与 Edge 共用引擎；这一点说明有调用平台媒体组件的路径，但 GPU 渲染成功不能证明视频硬解已启用。[3][4] `isConfigSupported()` 成功和 `hardwareAcceleration: "prefer-hardware"` 也不能作为硬解证明，规范允许浏览器忽略该提示。[5]

因此，本次没有为 AV1 重编客户端 EXE 的必要改动。现有客户端加载 1.90 NAS 页面后即可尝试 AV1；实际能否硬解仍取决于本机 GPU、驱动、WebView2 Runtime、运行环境以及实际视频 profile / level。

### 诊断真实客户端会话

页面提供：

```javascript
await window.selkiesAv1.ready;
console.table({
  secureContext: window.isSecureContext,
  videoDecoderAvailable: typeof window.VideoDecoder === "function"
});
console.log(window.selkiesAv1.diagnostics());
```

诊断对象的 `supported` / `reason` 是能力探测结果，`session.framesDecoded`、`session.codec`、`session.output`、`session.state` 表示当前或最近一次 AV1 解码会话。`hardwareVerified: false` 表示页面没有证明实际硬解，并不等于已经判定为软件解码。诊断不包含输入内容、码流载荷或连接 URL。

发行版客户端没有启用 Tauri devtools feature，不应默认认为 F12 能打开调试器。可以按 Microsoft 官方的 WebView2 调试方法，在一次临时启动中附加远程调试端口。[6] 客户端仓库的 `verify-downloads.mjs`、`verify-connection-frost.mjs` 已使用相同的进程环境方式。

1. 完全退出旧客户端。在 PowerShell 中以实际 EXE 路径替换下例路径，仅为本次启动增加调试参数：

   ```powershell
   $clientExe = "C:\Apps\AXiVer\axiver-client.exe"
   $previousWebViewArgs = [Environment]::GetEnvironmentVariable("WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS", "Process")
   try {
       $env:WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS = ($previousWebViewArgs + " --remote-debugging-port=9222").Trim()
       Start-Process -FilePath $clientExe
   }
   finally {
       if ($null -eq $previousWebViewArgs) {
           Remove-Item Env:WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS -ErrorAction SilentlyContinue
       }
       else {
           $env:WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS = $previousWebViewArgs
       }
   }
   ```

2. 查看 `http://localhost:9222/json/version` 获取实际运行内核版本，查看 `/json/list`，选择 URL 为 NAS 远端页面的 target；不要误选壳窗口、等待页或上传页。使用返回的 DevTools 链接，或通过 Edge 的设备检查界面附加该本机 target。
3. 先打开 DevTools 的 Media 面板，再切换 AV1 并进行聊天滚动 / 移动窗口。检查上面的诊断对象是否持续增加 `framesDecoded`，画面是否正确，codec 是否为 `av01...`。[7]
4. 检查 Media 日志中的具体 decoder / platform 信息，并结合任务管理器中该客户端 `msedgewebview2.exe` 对应的 GPU Video Decode 引擎活动。只有泛化包装器名称、只有 `supported: true`、只有 GPU 渲染或低 CPU，都不能单独证明 AV1 已走硬解；证据不足时结果仍为“未确认”。
5. 验证结束后退出本次调试启动的客户端，再按原方式启动。调试端口只用于本机临时核查。

HTTPS 页面仍需要 `isSecureContext === true`。若使用显式 HTTP 发现地址，WebCodecs 可能不可用；应以页面诊断结果为准。WebCodecs 仅在安全上下文开放。[7]

## 验证记录与实际边界

本次验证包括真实 AV1 码流解析、固定原生运行库 API 检查，以及直接执行项目函数的定向回归。测试中的模拟 VideoDecoder 用于覆盖生命周期、错误和资源回收，不能代替浏览器真实解码。

### 真实码流与原生运行库

- 使用 FFmpeg / libaom-av1 生成普通 8-bit 连续帧、1920×1080、1366×768、reduced still-picture 和 10-bit 反例。前端解析得到实际 level 与尺寸；10-bit 按本版支持范围拒绝。小型可重现样本与生成命令保存在 `tests/fixtures/av1_samples.json`，其中大尺寸和 10-bit 样本只收纳完整序列 OBU，用于解析验证，不能单独提交解码。
- 实际加载官方 PyPI 的 `pixelflux 2.2.3` CPython 3.12 manylinux wheel，核对 `CaptureSettings` 的 AV1 字段、`ScreenCapture`、`hardware_encoders()`、`hardware_formats()` 和 `stream_info()` 接口。
- 使用该真实运行库执行 AV1 适配器的无 GPU 路径，得到明确的编码能力拒绝，没有启动软件 AV1。该结果只验证缺失 GPU 时的处理，不代表 780M 硬编通过。
- 本环境没有可用的 Docker / 780M / Windows WebView2；浏览器执行受当前环境策略阻挡。因此没有容器构建、真实浏览器出帧、NAS 部署或客户端硬解性能的通过记录。

## 部署与验收

源码与 Compose 示例镜像版本更新为 `1.90`。保留现有 Compose 配置和 `/config`，从当前 `AXiVer` 源码构建并重建服务，随后重新加载客户端页面。项目的镜像工作流由 tag 或手动运行触发，推送分支不等于镜像仓库已发布 1.90。

选中 AV1 后，服务端日志应出现 `AV1 hardware session`，对应的 `stream_info()` 应有 `codec=av1`、`hardware=true`、`bit_depth=8`、`fullcolor=false`、`striped=false`。失败时查看明确的回退原因，界面应回到 H.264 并恢复画面。

实机验收应覆盖：静态中文小字、聊天滚动、图片 / 视频混合画面、1920×1080 和非整齐宽度、改分辨率、重新连接、隐藏后恢复、休眠唤醒、共享观看者加入及退出。比较 H.264 / HEVC / AV1 时固定分辨率和帧率，先比较同码率画面，再比较相近画质的带宽与 CPU / GPU 占用；不同编码相同 CRF 数字不代表相同质量。4:2:0 仍会损失部分彩色细字色度细节，AV1 不等于无损文字传输。
