# 1.88 中文输入偶发无响应修复

日期：2026-11-18（Asia/Shanghai）。基线：`AXiVer` / `85e79213b4a0d522730e83088149115bf142c616`（1.87）。

本次修复三个已由源码和回归模型确认的缺陷。没有取得用户故障瞬间的浏览器事件、NAS 日志或目标应用回执，因此不能断言每一次现场无响应都具有相同原因。

## 一、重连后旧队列堵住后续输入

原实现将未发送的文字及其后续按键绑定到原 WebSocket。连接更换后，`flushAssistInput()` 会保留原队列并返回失败；新提交仍加入同一个队列，导致连接恢复后继续输入也无法发送。

最小复现：

1. 原连接的 `bufferedAmount` 达到 262144，提交一段中文。
2. 在待发队列尚未排空时更换连接。
3. 在健康的新连接上重新组词提交。
4. 1.87 的新连接收不到文字，旧文字和新文字都留在原队列中。

现在将旧连接尚未发送的文字移入当前页面的恢复区，清理旧队列的按键动作；新连接上的新提交使用独立的发送队列。已经交给 `WebSocket.send()` 的段落不会再次重发。

组合输入也记录其开始时的连接。组合期间断线、失焦或更换连接时，迟到的最终候选保留供核对，不自动投递到新窗口；缺少 `compositionstart` 但存在预编辑事件的路径同样记录连接。

“妙妙小工具”增加“复制未发送文字”，只写入本机剪贴板。复制失败仍保留文字。输入法轻修复只恢复输入状态，不再顺带重放旧文字或旧回车。恢复内容只存在当前页面内存中，刷新或关闭页面前应先复制。

## 二、中文输入未更新活动状态

IME 防护在 `window` 的捕获阶段调用 `stopImmediatePropagation()`，阻止旧版输入监听器重复发送；同时也挡住了 `document` 上的活动监听器。原 `noteAssistInput()` 只更新焦点恢复冷却，没有更新待机活动时间或动态节流状态。

因此，纯中文组合、选词和候选导航可能持续发生，但系统仍将页面视为闲置。这是所有浏览器共用的前端逻辑缺陷，不依赖某个输入法品牌。

现在由接管事件的防护层主动更新活动状态，包括 keyCode 229、组合开始/更新/结束、原生文本插入和候选导航。沿用既有活动上报的限频与单请求合并，正文不会进入活动接口。发送重试、队列排空和清理定时器不算用户活动，不会持续阻止正常休眠。

## 三、坏剪贴板辅助格式使中文整次提交失败

X11 中文提交使用整段剪贴板粘贴。粘贴前需保存原剪贴板，但原 `_snapshot()` 要求每个宣告的格式都转换成功：即使 `UTF8_STRING`、PNG 或 HTML 已成功读取，一个额外的工具包私有格式拒绝转换也会使整次提交在触发粘贴之前失败。

现在优先保存常见格式，将非必要辅助格式的失败隔离。核心文本、图片、富文本等格式沿用共享总预算，不以缩短超时为代价丢弃可恢复的主数据。没有可保留数据、剪贴板所有者变化、核心格式无法保存或超出大小限制时，仍停止粘贴，避免覆盖原内容。

每次读取使用不同的请求窗口，且先分配下一次窗口再销毁上一次窗口。这个顺序是必要的：python-xlib 会立即复用最后释放的资源编号，简单的“新建—销毁—再新建”不能隔离迟到回复。保留最近一个请求窗口使编号保持不同；窗口数量有界，不随输入次数累计。

回归覆盖迟到的 `SelectionNotify`、拒绝回复和 INCR 分块事件，按请求窗口与格式匹配。既有目标应用读取回执、剪贴板恢复及不自动重试已触发粘贴的规则继续保留。

协议与实现参考：

- [X.Org ICCCM：Selection 与 INCR 约定](https://xorg.freedesktop.org/archive/X11R7.6/doc/xorg-docs/specs/ICCCM/icccm.html)
- [python-xlib 资源编号分配](https://github.com/python-xlib/python-xlib/blob/master/Xlib/protocol/display.py)
- [python-xlib 窗口销毁与编号释放](https://github.com/python-xlib/python-xlib/blob/master/Xlib/xobject/drawable.py)
