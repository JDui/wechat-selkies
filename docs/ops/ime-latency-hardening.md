# 高延迟输入测试与修复

## 复现结果与修改

上一版在缓冲积压时对后续按键执行 `preventDefault()`，既未发送也未排队。新建 `tests/test_ime_latency.js` 在修改前复现 6 项中 4 项失败：有发送积压的两档延迟、客户端停顿，以及积压在 keydown/keyup 之间解除时，英文或 Enter 缺失。低延迟和无积压的延迟场景通过。

现在复用现有 WebSocket 包装器，将积压文字之后的 `kd/ku/kr` 与 `co,end` 放入同一个 FIFO。只有浏览器接受的包才出队，失败保留当前包；内部分发有重入保护，连接更换后保留队列，继续要求用户恢复远端焦点后显式修复。此修改不增加远端回执，也不重放已被 `send()` 接受的包。

另修复上一轮极端测试留下的两类前端问题：去重状态不能跨 assist 元素，也不能因新输入文字相同就丢弃独立粘贴；blur 或 assist 更换会退出残留的 composing 状态，未完成拼音不会因此自动发送。

复现命令：

```text

node tests/test_ime_extreme.js

```

真实 WebSocket 检查使用已安装的 Python `websockets` 和 Node 内置客户端，只监听 `127.0.0.1`，退出时终止测试服务。缓冲繁忙值由测试注入；100/500ms 是服务端应用读取等待，不是测得的公网 RTT。虚拟时钟用例中的 RTT/处理延迟是确定性模型参数，不是网络或 CPU 性能实测。

虚拟模型使用共享时钟；15s 停顿也会延后模型中的传输和处理回调，用来检查过期计时器恢复后的顺序，不代表独立服务器仍在运行时的客户端停顿测量。真实 CPU 压力由下面的独立容器试验覆盖。

## 容器与验收边界

Luna Max 子线程使用现有本地镜像、临时容器及 Xvfb/xdotool/xterm 做限 CPU 与后台负载检查，结果记录在 [容器 CPU 压力反馈](ime-container-stress-feedback.md)。不启动微信或 QQ，不触碰用户已有容器。

压力试验确认：命令返回码为 0 仍可能实际少字符，必须检查窗口捕获内容。尝试单纯增加 `type --delay`、仅拆成逐码点子进程或增加进程间等待都出现过复测失败，因此未将单次通过当作最终证明。

当前后端改用现有 `xdotool key` 的 Unicode keysym 路径，ASCII 仍用 `type`，Wayland 仍用 `wtype`。这一方向有上游源码依据：`type` 限制按下阶段最多 50ms，而 `key` 用请求间隔的一半作为按下阶段；但上游 master 不等于镜像安装版本，最终可靠性判断依靠本地镜像中的真实窗口对照。[上游 xdo.c](https://github.com/jordansissel/xdotool/blob/master/xdo.c)

最终实际代码路径在同一个 0.5 核限额、两路后台 CPU 负载持续存活的容器中，完整捕获单条 128/128，以及下一条 128 码点消息紧接“中文”的 130/130；纯 ASCII 对照 128/128。17 项 Python 定向检查通过，临时容器清理完成。Unicode 消息创建进程和通信共享最多 60 秒预算，其他路径仍最多 30 秒；没有改变传输协议或使用剪贴板。

这项可靠性修复有明显吞吐代价：128 码点混合串空闲时约 18.17 秒，受压时 22.67 秒，128 码点紧接短词合计 23.51 秒。当前优先避免缺字，没有声称这些等待开销已经优化，也没有声称对所有调度器或应用保证完整。

所有检查都不能代替真实浏览器原生 IME 与已登录聊天窗口验收。此轮源码修复未构建发布镜像或部署到用户容器。
