# 文字输入加固

本轮修复源代码，尚未部署验证真实输入法与微信 / QQ。

## 代码确认的问题

- 旧补丁在所有 `input` 事件中立即 flush、清空隐藏输入框，未区分 IME 的预编辑和最终提交。
- 随附 bundle 只有 `_typeString` 调用，没有该方法实现。旧补丁重试期间，上游其他 `input` 监听器仍可能逐字发送并清空输入框，重试无法保证保留文本。
- 上游窗口键盘监听器会阻止组合输入按键的默认行为；隐藏输入框还有直接转发 Enter / Backspace 的旧监听器。
- 服务端 `co,end` 固定 0.5 秒超时，没有在超时后终止文字注入进程，长句可能继续在后台输入并与后续按键交错。

这些是本地事件处理和注入的缺陷，不能据此认定发生了网络丢包。现有实现也没有远端应用确认文字上屏的回执。

## 当前行为

- 在上游监听器注册前安装窗口捕获监听，覆盖后续创建或重新创建的隐藏输入框。
- 组合期间保留预编辑，在 `compositionend` 中立即保存事件的 `data`，不等待计时器读取可变的输入框。只有清理输入框的操作延迟执行，末尾 `input` 事件不会重复发送已保存的词。取消组词不发送内容，连续相同文本按两次输入处理。
- 候选词选择用的 Enter、Backspace 等按键留给本地 IME，不阻止默认行为，不传到远端。普通按键与快捷键仍走原链路。
- 复用现有 WebSocket `co,end` 协议，每段最多 128 个 Unicode 码点，不拆开表情或扩展汉字。服务端按原消息循环顺序处理文本和后续按键。
- 未发送内容进入页面内存队列；缓冲超过 256 KiB 或同步发送失败时，120ms 后重试。仅重试尚未被 `send()` 接受的段，避免重复输入。有连接但文字积压时，后续原生 `kd/ku/kr` 进入同一 FIFO，保留文字、英文和 Enter 的先后顺序。尚无连接时，可打印字符继续通过本地输入框保留；不主动重放离线操作键。
- 连接更换后暂停自动重放并显示提示。先恢复远端输入框，再用“输入法轻修复”，下次按键会尝试发送保留内容。开发排查可调用 `window.selkiesRecoverPendingInput()` 读取尚未发送的内容；不会自动打印文字，也不写入持久存储。刷新或退出页面会丢失这份内存内容。
- 文字注入超时根据长度调整，X11 Unicode 消息共享最多 60 秒，纯 ASCII 和 Wayland 最多 30 秒；进程创建和通信共用预算。失败记录退出状态或异常类型，超时或取消会终止并回收进程。失败或结果不确定时不自动重放。
- 更新覆盖脚本缓存版本 `1.75-ime-1`。

`send()` 成功只表示浏览器接受了消息，并不证明远端聊天框已经收到文字。跨断线的严格一次投递仍需要额外的确认协议，本次没有宣称提供这一保证。

## 最小验证

运行 `node tests/test_ime_delivery.js` 和 `python -m unittest tests.test_text_injection`，覆盖组词/取消/提交顺序、候选 Enter、重复输入、Unicode 分段、背压、部分发送失败、连接更换，以及服务端超时与取消清理。

## 2026-10-24 回归修复

用户反馈连续拼音选词后整词或几个字缺失。上一版隔离检查没有覆盖 `compositionend.data` 与 DOM 值不同，以及下一轮组词先于零延迟计时器开始的情况。

新增检查在修复前复现了：`compositionend.data` 为“中文”但输入框已空时，没有任何文字发出。修复改为在结束事件内保存提交内容，并将提交队列与实时预编辑字段分开。另补齐紧接下一轮组词、取消时仍残留拼音、延迟最终 `input`、重复确认同一词和背压期间继续输入的检查。这里确认的是可复现的代码缺陷，尚不能断言它解释了用户环境的全部漏字。

这些为隔离事件与进程测试；未启动真实 OS 输入法、X11、微信或 QQ。部署后重点复核：连续拼音选词、用 Enter 确认候选、长句、快速重复提交、表情、短时断线。无须据此执行大规模性能测试。

## 极端场景检查

前端在原有 fixture 上补充 `node tests/test_ime_extreme.js`，覆盖独立同文插入、DOM 重建、丢失结束事件、候选按键、发送缓冲边界、逐段失败与恢复，以及 1,000 次固定种子的组合提交。服务端运行 `python -m unittest tests.test_text_injection tests.test_text_injection_extreme`，覆盖 Unicode、大文本、启动/通信异常、退出状态、取消竞态、超时上限和日志正文保护。

极端检查不修改生产代码、不将失败标记为预期通过；退出码非零表示仍有未解决的断言。Luna Max 子线程的分类反馈、最小复现与模拟限制见 [极端测试反馈](ime-extreme-test-feedback.md)。

## 2026-10-25 高延迟与 CPU 压力修复

本轮按用户要求进一步修改生产代码，详见 [高延迟测试与修复](ime-latency-hardening.md) 和 [容器 CPU 压力记录](ime-container-stress-feedback.md)。前述“极端检查不修改生产代码”指上一轮只收集反馈的工作。

文字积压时的后续按键现纳入同一发送队列，避免英文与 Enter 被拦后永不补发。同文去重限定为同一个 assist 的 composition 尾随事件，避免吞掉新的粘贴或替换；失焦与 assist 更换会释放已中断的组合状态。

真实容器中确认旧 X11 Unicode 注入可能返回成功却缺字；最终改用逐码点 `xdotool key --delay 200 UXXXX`，ASCII 保留快速 `type`，不借用剪贴板。0.5 核限额加两路后台负载下，完整捕获两轮 128/128、130/130；17 项 Python 检查通过。代价是长 Unicode 注入明显变慢：该测试 128 码点混合串空闲约 18 秒，受压约 23 秒。不能据此声称真实微信输入法已经验收。
