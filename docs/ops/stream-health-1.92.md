# 1.92 画面稳定性与状态点

日期：2026-11-18（Asia/Shanghai）。基线：`AXiVer` / `fe920ee46ec0bb944c5932032d751940461cec98`（1.91）。

本轮针对“连接仍在但画面偶发停住”的报告，修复可从源码和故障回归证明的问题，并为最左侧变色状态条增加上红、下紫两个状态点。没有目标 NAS 的运行日志或网络抓包，不能断言用户此前每次卡顿都由同一个原因造成，也没有声称已完成 780M / WebView2 实机故障验收。

## 状态点

| 位置 | 状态 | 触发依据 |
| --- | --- | --- |
| 上方红点 | 传输异常或视频丢帧 | 服务端视频队列溢出导致重同步、无效视频包、已有媒体会话的异常断流 |
| 下方紫点 | 画面卡顿 | 已收到的视频长时间未呈现、解码或绘制异常、接收 ACK 超时、前台视频活动期间的明显事件循环阻塞 |
| 中间变色条 | 原有动态节流 / 鼠标状态 | 保留原有逻辑 |

平时两点为低亮度灰色；发生异常时按对应颜色闪烁。事件结束后保留约 2.4 秒提示，持续异常可以延长提示；每类计数每秒最多增加一次。鼠标悬停状态条可查看说明。减少动态效果偏好下改为短暂常亮，不强制闪烁。点不拦截鼠标，也不会被中间彩虹动画改色。

浏览器 WebSocket API 不提供底层 IP 丢包计数。因此红点的口径是可确认的应用视频丢弃或传输异常，不显示伪造的“网络丢包率”。高 RTT、帧号跳跃、16 位回绕、同帧分片、JPEG 正常主动降帧、首次加入共享、正常切换连接均不直接点亮红点。[WebSockets 标准](https://websockets.spec.whatwg.org/)

## 修复的具体路径

### 绘制与解码

- 原绘制分支遇到 `drawImage()` 或 `VideoFrame.close()` 异常时，可能跳过下一次 `requestAnimationFrame()`，永久停止画面刷新。现逐帧释放资源，并在 `finally` 中继续调度；反复 MODE 初始化也只维持一条绘制循环。
- H.264 / HEVC 的异步能力探测、输出、错误和超时回调核对解码器实例。重置或尺寸变化后，旧回调不能配置、删除或关闭新实例。
- 每个 stripe decoder 的待配置与在途帧共享 48 帧 / 32 MiB 上限，单包上限 16 MiB。仅有待输出视频时才启动 8 秒无输出检测，静态画面不因长期没有新内容而重启。
- 每个解码输入使用唯一 timestamp 对应真实帧元数据，避免所有输出沿用解码器创建时的首帧 ID。绘制前只保留各位置最新的已解码画面，编码参考帧仍按顺序提交。
- HEVC 顶层能力探测增加 3 秒超时，避免浏览器探测迟迟不返回时卡住整个客户端启动；存储拒绝也不能阻断 H.264 回退。

### 接收确认与服务端背压

- 副屏原先在背压期间仍从队列取出并丢弃参考帧；现在所有显示器都暂停消费，保持编码帧顺序。
- `CLIENT_FRAME_ACK` 仍表示累计接收确认，不改成部分编码专用的绘制确认。服务端只接受当前显示器 owner 的合法 ACK，并用实际发送记录计算未确认帧数量。
- 同帧分片、帧号跳变和回绕按发送顺序处理；重复 ACK 不会不断延长接收进度计时，无待确认数据的静态画面不会被判停滞。
- 有未确认数据且 4 秒无进展时提示 `ack_timeout`；8 秒仍无进展时尝试恢复视频，30 秒冷却。恢复执行前重新核对连接、显示器、capture、queue、ACK 进度及停止 / 休眠状态。
- 恢复失败需要全量重配置时，先释放捕获锁，再执行带状态快照检查的回退。进入锁后发现连接替换、主动停止、休眠或捕获实例变化则放弃旧请求，避免恢复被跳过或旧任务复活画面。

### 真实呈现与自动恢复

- AV1 type 6 已纳入视频接收观察。
- 原 FPS 数值包含接收帧计数，不能证明解码或绘制成功。看门狗现在使用实际成功绘制的回调，不再让高接收 FPS 掩盖冻结。
- `VIDEO_STARTED` 和 JSON `pipeline_status` 只表示管线状态，不宣布画面已经恢复。相同状态通知幂等，不能反复清空待呈现数据、延长宽限。
- 新连接、明确重置、隐藏页面恢复和 STOP → START 提供 3 秒观察宽限。宽限后已有待呈现视频持续 500 毫秒以上可点亮紫点；持续异常由原有渲染看门狗阈值决定恢复，默认 12 秒。
- 前台视频活动期间的事件循环阻塞会提示紫点，并重新提供观察宽限；页面已经恢复执行时，不仅因过去阻塞过就重启视频。
- 主控自动恢复发送 `FORCE_STREAM_RECOVER,<当前显示器>,video`，优先局部重建视频；局部捕获无法建立时进入受保护的全量显示重配置回退。共享观看只请求 `START_VIDEO` 取得新的共享关键帧。自动恢复不发送输入模块重置、释放按键、音频重启或桌面服务重启命令。手动完整修复流程保留。
- 已替换连接的晚到视频、角色和控制消息在 runtime 中被隔离，不能关闭当前画面的监控或覆盖新身份。

## 诊断接口与开销

在当前远程页面的开发者工具中执行：

```javascript
window.__selkiesStreamHealth.diagnostics()
```

可查看当前点亮状态、最后原因码、各显示器收到 / 呈现次数、待呈现数量和停滞时长。`framesRendered` 记录成功绘制回调；分片画面可能一个编码帧对应多个绘制回调，不能把它直接当成完整画面 FPS。

健康状态最多保存 4 个显示器、每个显示器 256 条纯帧元数据。它不保留视频内容、URL、输入内容或无限历史。只有一个 250 毫秒采样定时器；界面仅在提示状态变化时更新，反复挂载不会增加状态点或定时器。

服务端提示协议：

```text
STREAM_HEALTH,{"kind":"drop","reason":"video_queue_overflow","display_id":"primary"}
STREAM_HEALTH,{"kind":"stall","reason":"ack_timeout","display_id":"primary"}
```

服务端每显示器、每类最多 5 秒一次。主屏提示发送给主控与共享观看，副屏提示只发送到对应连接。提示本身不会触发恢复，也不会被客户端回传。诊断回调或提示发送异常不阻断视频处理。

## 回归与目标机器验收

新增行为回归覆盖：实际绘制异常后继续刷新、解码器旧回调、配置超时、队列边界、ACK 重复 / 回绕 / 跳号、无 ACK 首帧、静态画面、后台 / 暂停、角色与副屏隔离、JSON 状态、旧连接消息、重配置失败与锁释放、提示点重复挂载与彩虹样式隔离。

本轮定向验证通过 122 项 Python 测试和 18 个 JavaScript 测试脚本。新增服务端恢复测试还包含六个恢复入口 × 三种失败情况，以及六种排队后连接 / 状态变化子场景；健康状态模块包含 20 组行为回归。旧鼠标悬停测试夹具已同步加载状态点函数，原有鼠标驻留、动态节流与彩虹指示回归仍通过。

这些回归执行实际发布源码中的函数，并用可控故障模拟 VideoDecoder、Canvas、连接、时间和设备状态。当前开发环境没有目标 NAS 的 Docker / GPU，也未运行真实浏览器故障演练；DOM / CSS 回归不等于各浏览器截图验收。

部署 1.92 镜像后，建议按以下顺序观察：

1. 静态聊天窗口停留，正常情况下两点不持续闪烁、不自动重建视频。
2. 滚动聊天、切换图片，分别使用 H.264、HEVC、AV1，观察异常时上下点和实际画面是否一致。
3. 正常隐藏 / 恢复页面、主动暂停 / 恢复视频、共享加入和副屏切换，不应被当成网络丢包。
4. 在测试连接上制造短暂网络中断或解码阻塞后恢复，核对是否恢复到原画面，以及输入状态、音频和其他显示器是否保留。
5. 若仍冻结，保存当前页面的健康诊断、服务端同期日志以及 1.91 的会话诊断，按传输、解码、绘制三个阶段定位。

本轮不修改端口、密码、网络、设备映射或 `/config` 卷。源码与示例标签更新为 1.92；分支推送不表示镜像已构建、已发布或 NAS 已部署。
